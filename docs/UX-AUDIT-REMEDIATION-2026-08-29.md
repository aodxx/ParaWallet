# รายงานความบกพร่องด้าน UX และแผนแก้ไข ParaWallet

สถานะ: **งานบังคับ — ต้องแก้ครบทั้ง 7 ชุดก่อนเริ่มฟีเจอร์หรือปรับภาพลักษณ์ใหม่**  
วันที่ตรวจ: 29 สิงหาคม 2026  
ขอบเขต: PWA บนมือถือ ทั้งหน้าคนกรีดและเจ้าของสวน  
รุ่นที่ตรวจ: `main` หลัง Deploy `2026.08.29-ocr-scan-ux-v6`

## 1. วัตถุประสงค์

เอกสารนี้เป็นแผนแก้ UX ฉบับเดียวที่ทีมต้องใช้อ้างอิงหลังการ Deploy ล่าสุด โดยไม่เปลี่ยนกติกาการเงินหรือสิทธิ์ของแต่ละบทบาท เป้าหมายคือให้ทุกขั้นตอนตอบคำถามต่อไปนี้ได้โดยผู้ใช้ไม่ต้องเดา:

1. หน้านี้ทำอะไรได้?
2. ตอนนี้ระบบกำลังทำอะไร?
3. ทำสำเร็จหรือไม่สำเร็จ?
4. ผู้ใช้ต้องทำอะไรต่อ?

งานจะไม่ถือว่าเสร็จเพียงเพราะหน้าจอสวยขึ้น ต้องแก้พฤติกรรม คำภาษาไทย สถานะ ความผิดพลาด เส้นทางตามบทบาท การทดสอบ และผ่านการยอมรับบนมือถือจริงตามเอกสารนี้ด้วย

## 2. หลักฐานและข้อจำกัดของการตรวจ

- ตรวจหน้า Login สาธารณะที่ `https://aodxx.github.io/ParaWallet/` หลัง Deploy แล้ว
- ตรวจหน้าหลังเข้าสู่ระบบจาก React source เดียวกับที่ Merge เข้า `main` เนื่องจากหน้าคนกรีดและเจ้าของสวนต้องใช้บัญชี Google ที่ลงทะเบียนและมีสิทธิ์ในสวน
- ยึดกติกาเดิม: เจ้าของสวนต้องไม่เห็นงานเฉพาะคนกรีด, คนกรีดต้องเห็นกระเป๋าคู่และการเพิ่มรายการขายเป็นงานหลัก, การเงินต้องผ่านการตรวจ backend และการยืนยันของทั้งสองฝ่าย
- รายงานนี้ตรวจการนำทาง คำศัพท์ สถานะ การตอบกลับ Empty/Error/Loading ลำดับงาน และการจัดข้อมูล ไม่ใช่หลักฐานรับรองความแม่นยำ OCR จากบิลจริง

## 5. งานแก้ไขบังคับ 7 ชุด

### ชุดที่ 1 — แก้คำศัพท์และเมนูให้ตรงกับบทบาท

สถานะ: ✅ ดำเนินการแล้ว พร้อม contract tests สำหรับคำศัพท์ เมนู และคำสั่งที่อนุญาตตามบทบาท

สิ่งที่ต้องทำ:

- ใช้ “เจ้าของสวน” และ “คนกรีด” ในหน้าปกติ ลด `(Owner)` และ `(Tapper)` ที่ซ้ำทุกจุด
- ฝั่งคนกรีดใช้ **เพิ่มรายการขาย** เป็นงานหลักหนึ่งงาน แล้วให้เลือก 3 วิธี: **ถ่ายภาพบิล**, **เลือกภาพจากเครื่อง**, **กรอกตัวเลขเอง**
- ฝั่งเจ้าของเปลี่ยน **ส่งเงิน** เป็น **รับเงิน** และชื่อหน้าเป็น **เงินที่คนกรีดส่งมา**
- เปลี่ยนเมนูคนกรีดจาก **สวนและสมาชิก** เป็น **ข้อมูลสวน**
- เปลี่ยนกระเป๋าเจ้าของเป็น **ส่วนแบ่งทั้งหมดของฉัน**, **ได้รับแล้ว**, **ยังอยู่กับคนกรีด**
- ห้ามแสดงคำสั่งที่บทบาทปัจจุบันไม่มีสิทธิ์ทำ

ไฟล์หลัก: `src/App.tsx`, `src/styles.css`, `tests/role-ui-contract.test.ts`, `docs/PARAWALLET-REAL-USE-MANUAL.md`

เกณฑ์รับงาน:

- ผู้ทดสอบคนไทย 5 คนระบุงานหลักของบทบาทได้โดยไม่ต้องอธิบาย
- Owner ไม่มีปุ่มสร้าง/สแกน/ส่งเงินของคนกรีด
- Tapper ไม่มีปุ่มจัดการสมาชิกหรือยืนยันแทนเจ้าของ
- Contract test ตรวจทั้งคำที่ต้องมีและคำสั่งต้องห้ามของแต่ละบทบาท

### ชุดที่ 2 — สร้างระบบสถานะกลางเพียงแบบเดียว

สถานะ: ✅ ดำเนินการแล้ว พร้อม typed status contract, action/connection/authentication scopes และ regression tests

สิ่งที่ต้องทำ:

- เปลี่ยน `message` แบบข้อความอิสระเป็น Typed state: `idle`, `working`, `success`, `partial`, `empty`, `offline`, `auth_error`, `api_error`
- ทุกสถานะต้องมีหัวข้อ คำอธิบายไทย ขั้นตอนถัดไป retryable และกติกาการปิด
- หนึ่งเหตุการณ์แสดงหนึ่งตำแหน่ง ห้ามซ้ำทั้ง Global banner และในหน้า
- หน้า Signed-out ปกติเป็นคำแนะนำ ไม่ใช่ Error
- ปุ่มต้องแสดง “กำลัง...” และป้องกันกดซ้ำระหว่างบันทึก
- Partial/Offline ใช้ข้อมูลล่าสุดได้ แต่ต้องบอกเวลาโหลดล่าสุด
- ทุกฟอร์มและรายงานต้องแสดง Error จริง ห้าม catch แล้วเปลี่ยนเป็น Empty

ไฟล์หลัก: `src/App.tsx`, `src/api.ts`, `src/styles.css`, `tests/role-ui-contract.test.ts` และ API error tests

เกณฑ์รับงาน:

- Async action ทุกจุดเริ่มด้วย Working และจบด้วย Success หรือ Error ที่เฉพาะเจาะจง
- Failed request ไม่กลายเป็น Empty
- Success ไม่มีปุ่ม “ลองใหม่”
- สถานะ Connection, Action และ Authentication ไม่เขียนทับกัน

### ชุดที่ 3 — ให้งานรอตรวจและรายการล่าสุดมาก่อนปฏิทิน

สถานะ: ✅ ตรวจซ้ำและแก้ครบแล้ว — รายการรอตรวจ/ล่าสุดแสดงเป็น Card ก่อนปฏิทิน, Dashboard ส่ง Filter รอตรวจ, Notification ใหม่มี Entity ID และเปิด Sale/Settlement ตัวจริงก่อนทำเครื่องหมายว่าอ่านแล้ว

สิ่งที่ต้องทำ:

- หน้า Sale มีแท็บ **รอตรวจ**, **ล่าสุด**, **ยืนยันแล้ว**, **ทั้งหมด**
- Owner เปิด **รอตรวจ** เป็นค่าเริ่มต้นเมื่อมีงาน; Tapper เปิด **ล่าสุด**
- ปฏิทินเป็นมุมมองเสริม ไม่ใช่ทางเดียวในการหารายการ
- ปุ่มงานรอตรวจจาก Dashboard ต้องส่ง Filter และ Focus/Open งานที่เกี่ยวข้อง
- Notification ต้องเปิด Sale/Settlement ตัวจริง ทำเครื่องหมายอ่านแล้วหลังหาเป้าหมายสำเร็จ หรือคืนสถานะเมื่อเปิดล้มเหลว
- เรียง Pending ก่อน Completed และบอกทุก Card ว่า “รอใครทำอะไร”

ไฟล์หลัก: `src/App.tsx`, `src/api.ts`, `src/styles.css`, tests และ `appsscript/Code.gs` เฉพาะกรณี Notification ขาด Entity ID

เกณฑ์รับงาน:

- Owner เข้าถึงงานยืนยันจาก Overview ได้ภายในไม่เกิน 2 Tap
- Notification เปิดรายการนั้นโดยตรง
- เห็น Sale ล่าสุดโดยไม่ต้องเลือกวัน
- ปฏิทินยังใช้งานได้และ Date/timezone tests เดิมต้องผ่าน

หมายเหตุการแก้หลังตรวจ commit `d212532`: implementation แรกมีแท็บแล้วแต่ยังส่งรายการทั้งหมดเข้า `SalesCalendar` ทำให้ผู้ใช้ต้องเลือกวัน และ Notification มีเพียง `targetScreen` จึงเปิดได้แค่หน้ารวม รุ่นแก้ไขเพิ่มรายการ Card ที่เปิดได้ทันทีและ structured notification payload ในคอลัมน์ `body` เดิมเพื่อรองรับ Entity ID โดยไม่เปลี่ยน Schema ของ Google Sheets; การแจ้งเตือนเก่ายังเปิดหน้ารวมพร้อมคำอธิบายอย่างโปร่งใส

### ชุดที่ 4 — แสดงใบสรุปหลังทุกการบันทึกหรือยืนยัน

สถานะ: ✅ ดำเนินการแล้ว พร้อม completion receipt หลัง mutation และ in-app dialog สำหรับคัดค้าน/ปฏิเสธ/ยกเลิกรายการ

สิ่งที่ต้องทำ:

- หลังสร้าง Sale แสดงยอด ชนิดยาง วันที่ สถานะ **รอเจ้าของตรวจ** และปุ่ม **ดูรายการนี้** / **กลับหน้าหลัก**
- หลังส่งเงิน แสดงยอด วิธีส่ง สถานะหลักฐาน และ **รอเจ้าของยืนยันรับเงิน**
- หลัง Owner ยืนยัน/ปฏิเสธ ต้องสรุปว่ายอดกระเป๋าหรือยอดคงค้างเปลี่ยนอย่างไร
- เปลี่ยน `prompt()` เป็น Dialog ในแอป มีเหตุผลบังคับ ผลกระทบ ยกเลิก และยืนยัน
- Success อยู่จนผู้ใช้รับทราบหรือเลือกไปหน้าถัดไป ไม่ถูก Refresh ลบทันที

ไฟล์หลัก: `src/App.tsx`, `src/styles.css`, `tests/role-ui-contract.test.ts`, `tests/core.test.ts`

เกณฑ์รับงาน:

- ทุก Mutation ที่สำเร็จบอก Record และสถานะใหม่
- ไปยัง Record ที่เพิ่งเปลี่ยนได้ทันที
- ยกเลิก Dialog แล้วไม่มี API call
- กดซ้ำไม่สร้างรายการซ้ำ

### ชุดที่ 5 — ลบหรือเชื่อมปุ่มที่กดแล้วเงียบ

สถานะ: ✅ ดำเนินการแล้ว ปุ่มเมนูมือถือและปุ่มข้อมูล/การตั้งค่าเชื่อมกับ More sheet และเพิ่ม contract coverage

สิ่งที่ต้องทำ:

- เชื่อมปุ่มสามขีดมือถือกับ More sheet หรือลบออก
- ลบ Settings จนกว่าจะเปิด Deferred scope หรือแสดงเป็นข้อมูลที่ไม่ทำตัวเหมือนปุ่ม
- ตรวจ `button`, link, icon button และ card action ทุกตัวว่ามีผลที่เห็นได้
- เพิ่ม Contract test กันปุ่มเงียบ และทดสอบ Keyboard/Touch จริง

ไฟล์หลัก: `src/App.tsx`, `src/styles.css`, `tests/role-ui-contract.test.ts`

เกณฑ์รับงาน:

- ไม่มี Control ที่มองเห็นแต่ไม่มี Handler/Destination
- Icon-only control มีชื่อภาษาไทยสำหรับ Screen reader
- Disabled control บอกเงื่อนไขที่ขาดอยู่ใกล้ปุ่ม

### ชุดที่ 6 — แยก Loading, Empty, Error, Offline และไม่มีสิทธิ์

สถานะ: ✅ ดำเนินการแล้ว เพิ่ม actionable empty state สำหรับรายการขาย และคง typed connection/action state สำหรับ loading, partial, offline, API error และ unauthorized

สิ่งที่ต้องทำ:

- เลิกใช้ `Empty` ข้อความเดียวทุกหน้า เปลี่ยนเป็น Page state เฉพาะ
- Empty ต้องบอกสภาพจริงและปุ่มถัดไปที่บทบาทนั้นทำได้
- Report Error แสดง Error และ Retry; รายงานสำเร็จแต่ไม่มี Row ต้องบอก “ไม่พบรายการในช่วงนี้”
- Loading บอกว่ากำลังโหลดอะไรและรักษา Layout ไม่ให้กระโดด
- ไม่มีสิทธิ์/ไม่มีสวน บอกว่าใครเป็นผู้ให้สิทธิ์โดยไม่โชว์ Technical code

ตัวอย่างที่ต้องมี:

| สถานะ | หัวข้อ | ขั้นตอนถัดไป |
|---|---|---|
| คนกรีดไม่มี Sale | ยังไม่มีรายการขาย | เพิ่มรายการขาย |
| Owner ไม่มี Pending | ตรวจครบแล้ว | ดูรายการล่าสุด |
| ไม่มี Settlement | ยังไม่มีประวัติการส่งเงิน | ปุ่มตามสิทธิ์หรือไม่ต้องมีปุ่ม |
| API Error | โหลดรายการไม่สำเร็จ | ลองใหม่ |
| Offline มี Cache | กำลังแสดงข้อมูลที่โหลดล่าสุด | เชื่อมต่อใหม่ |
| ไม่มีสิทธิ์สวน | บัญชีนี้ยังไม่ได้รับสิทธิ์เข้าสวน | ติดต่อเจ้าของสวน / เปลี่ยนบัญชี |

ไฟล์หลัก: `src/App.tsx`, `src/api.ts`, `src/styles.css`, `tests/role-ui-contract.test.ts`

เกณฑ์รับงาน:

- QA บังคับแต่ละสถานะแล้วแยกออกจากกันได้โดยไม่อ่าน Console
- Empty ไม่พูดเรื่อง Connection เมื่อเชื่อมต่อปกติ
- Error ไม่ลบข้อมูลล่าสุดโดยไม่อธิบาย

### ชุดที่ 7 — ตัดภาษาทางเทคนิคและเพิ่มความอ่านง่าย

สถานะ: ✅ ดำเนินการแล้ว ปรับข้อความ OCR/ดาวน์โหลดตาราง/ข้อตกลงฉบับที่ และซ่อน raw backend status ด้วย fallback ภาษาไทย

สิ่งที่ต้องทำ:

- เปลี่ยน `OCR n%` เป็น **ระบบอ่านข้อมูลได้ n%** และย้ำว่าต้องตรวจภาพ
- เปลี่ยน **ส่งออก CSV** เป็น **ดาวน์โหลดตาราง**; ชนิดไฟล์อยู่ใน Helper text ได้
- เปลี่ยน Agreement ID เป็นเวอร์ชันและวันที่มีผล
- Map Backend status เป็นไทยครบ ห้ามแสดง Raw fallback
- Provider, Warning code, Request ID และ Model อยู่ใน **ข้อมูลสำหรับผู้ดูแลระบบ** ที่พับไว้
- ข้อความสำคัญบนมือถือเล็กต้องอย่างน้อย 12 px; Action และยอดสำคัญต้องใหญ่กว่า
- ตรวจ Contrast กลางแจ้งและ Touch target อย่างน้อย 44 px

ไฟล์หลัก: `src/App.tsx`, `src/ocr.ts`, `src/styles.css`, tests และคู่มือใช้งาน

เกณฑ์รับงาน:

- หน้าปกติไม่มี Raw English status หรือ Implementation ID
- อ่านคำแนะนำสำคัญที่ความกว้าง 360 px ได้โดยไม่ Zoom
- ผู้ดูแลยังเปิดดูข้อมูลเทคนิคได้โดยไม่รบกวนงานผู้ใช้
