## 1. ขอบเขตและกติกาหลักฐาน

เอกสารนี้คือขั้นตอนหลังงานแก้ UX ทั้ง 7 ชุด ไม่ใช่ฟีเจอร์ชุดที่ 8 จุดประสงค์คือพิสูจน์ว่าหน้าจอที่ผ่านการตรวจอัตโนมัติแล้วใช้งานได้จริงบนมือถือของคนกรีดและเจ้าของสวน รวมถึงบอกทางออกที่เข้าใจได้เมื่อระบบผิดพลาด

- ใช้บัญชีทดสอบที่ได้รับอนุญาตและสวนสำหรับทดสอบแบบควบคุมเท่านั้น
- ห้ามสร้าง ยืนยัน ปฏิเสธ หรือลบข้อมูลการเงินจริงเพื่อให้เช็กลิสต์ผ่าน เว้นแต่เจ้าของสวนอนุญาตรายการทดสอบนั้นโดยตรง
- ห้ามใส่รหัสผ่าน, Token, API key, อีเมลเต็ม, ภาพบิล, สลิป หรือหลักฐาน production ลง Git repository
- เก็บภาพหน้าจอและหลักฐานจริงในพื้นที่ส่วนตัวที่ทีมอนุญาต ส่วนใน repository ให้บันทึกเพียงวันที่ ผู้ทดสอบ อุปกรณ์ ผล และรหัสหลักฐานที่ไม่เปิดเผยข้อมูลส่วนตัว
- Automated test ใช้ยืนยันสัญญาโค้ดเท่านั้น ห้ามใช้แทนผลทดสอบบนมือถือจริง
- หากผลไม่ตรง ให้หยุดที่ขั้นตอนนั้น บันทึกเวลา บทบาท การกระทำ Request ID (ถ้ามี) และข้อความผิดพลาดก่อนแก้โค้ด

| ผ่าน | ขั้นตอน | ผลที่ต้องเห็น | หลักฐานที่เก็บ |
|---|---|---|---|
| [ ] | เข้าสู่ระบบด้วยบัญชีคนกรีด | เห็นหน้าคนกรีดและเฉพาะสวนที่ได้รับสิทธิ์ | หน้าภาพรวมและชื่อบทบาท |
| [ ] | เปิดปุ่ม **เพิ่มรายการขาย** | เห็น 3 วิธี: **ถ่ายภาพบิล / เลือกภาพจากเครื่อง / กรอกตัวเลขเอง** | เมนูเลือกวิธี |

| [ ] | เลือกภาพจากเครื่องในรายการทดสอบที่อนุญาต | เห็นภาพ ตัวเลขที่อ่านได้ และคำเตือนให้ตรวจเทียบก่อนบันทึก | หน้าตรวจภาพ |
| [ ] | กรอกตัวเลขเอง | ฟอร์มบอกชัดว่าเป็นการกรอกเองและแสดง Error ใกล้จุดกรอกเมื่อไม่ครบ | ฟอร์มก่อน/หลังตรวจ |

| [ ] | เปิดรายการขายและรายการส่งเงินล่าสุด | เห็นข้อความว่าใครต้องทำอะไรต่อ เช่น **รอเจ้าของสวนตรวจหลักฐานและยืนยัน** | Card ของสองรายการ |

เกณฑ์ผ่าน: ผู้ทดสอบทำครบโดยไม่มีคนบอกตำแหน่งปุ่ม และอธิบายได้ว่ารายการยังไม่กระทบยอดยืนยันจนกว่าเจ้าของสวนจะตรวจ

## 4. มือถือเจ้าของสวน

เตรียมรายการทดสอบอย่างน้อยหนึ่งรายการต่อผลลัพธ์ที่ต้องตรวจ การทดสอบ “ยืนยัน” และ “ปฏิเสธ” ต้องใช้คนละรายการ ห้ามเปลี่ยนสถานะรายการจริงเพื่อทดสอบ

| ผ่าน | ขั้นตอน | ผลที่ต้องเห็น | หลักฐานที่เก็บ |
|---|---|---|---|
| [ ] | เข้าสู่ระบบด้วยบัญชีเจ้าของสวน | เห็นเฉพาะสวนและงานของเจ้าของบัญชี | หน้าภาพรวมและชื่อบทบาท |
| [ ] | กด **รายการขายรอตรวจ** จากหน้าภาพรวม | เข้าถึง Card รอตรวจได้ภายในไม่เกิน 2 ครั้ง และไม่ต้องค้นจากปฏิทิน | หน้ารอตรวจ |
| [ ] | เปิด Notification รายการใหม่ | เปิด Sale ตัวจริงก่อนเปลี่ยนเป็นอ่านแล้ว | Notification และรายละเอียด Sale |
| [ ] | ยืนยัน Sale ทดสอบ | ต้องติ๊กว่าตรวจหลักฐานและตัวเลขแล้ว จากนั้นเห็นใบสรุปและยอดใหม่ | ก่อนยืนยัน/ใบสรุป/ยอดหลังยืนยัน |
| [ ] | คัดค้าน Sale ทดสอบอีกใบ | Dialog อธิบายผลกระทบและบังคับระบุเหตุผล | Dialog และสถานะใหม่ |
| [ ] | กด **เงินที่คนกรีดส่งมารอยืนยัน** | เปิดรายการโอนหรือเงินสดที่รอตรวจได้โดยตรง | Card และหลักฐาน |
| [ ] | ยืนยันการรับเงินทดสอบ | ต้องตรวจสลิปหรือรับเงินสดจริงก่อนยืนยัน แล้วเห็นยอดคงค้างใหม่ | ก่อนยืนยัน/ใบสรุป/ยอดใหม่ |
| [ ] | ปฏิเสธการส่งเงินทดสอบอีกใบ | Dialog บอกว่ายอดคงค้างจะไม่ถูกตัดและบังคับเหตุผล | Dialog และสถานะใหม่ |

เกณฑ์ผ่าน: ผู้ทดสอบอธิบายได้ว่า **ส่วนแบ่งทั้งหมดของฉัน / ได้รับแล้ว / ยังอยู่กับคนกรีด** ต่างกันอย่างไร และทุกการเปลี่ยนสถานะมีใบสรุปที่เปิดรายการนั้นได้

## 5. Failure journey

กรณีที่ต้องบังคับ Error ให้ใช้ test fixture หรือสภาพแวดล้อมทดสอบ ห้ามปิดบริการ production, ลบหลักฐานจริง หรือแก้สิทธิ์ผู้ใช้จริงเพียงเพื่อให้เกิด Error

| ผ่าน | กรณีและวิธีทดสอบที่ปลอดภัย | ผลที่ต้องเห็น | ห้ามทำ |
|---|---|---|---|
| [ ] | **Offline:** โหลดข้อมูลสำเร็จก่อน แล้วปิดอินเทอร์เน็ตและกดลองโหลดใหม่ | **กำลังแสดงข้อมูลที่โหลดล่าสุด** พร้อมเวลาและปุ่ม **ลองใหม่** | ห้ามทำรายการการเงินซ้ำระหว่างไม่แน่ใจว่าคำขอแรกสำเร็จหรือไม่ |
| [ ] | **Login หมดอายุ:** ใช้ session ของบัญชีทดสอบที่หมดอายุ | **เข้าสู่ระบบใหม่อีกครั้ง** และ **เปลี่ยนบัญชี Google** | ห้ามแก้ Token หรือรหัสผ่านจริงเพื่อจำลองผล |
| [ ] | **API Error:** ใช้ endpoint จำลองหรือ network rule ในรอบทดสอบ | **โหลดข้อมูลไม่สำเร็จ** พร้อมรายละเอียดภาษาไทยและ **ลองใหม่** | ห้ามเปลี่ยน endpoint ของ production ที่ผู้ใช้อื่นกำลังใช้ |
| [ ] | **Empty:** ใช้บัญชี/สวนทดสอบที่ไม่มีรายการ | ข้อความเฉพาะหน้า เช่น **ยังไม่มีประวัติการส่งเงิน** หรือ **ไม่พบรายการในช่วงนี้** พร้อมทางไปต่อ | ห้ามแสดง Error เป็น Empty |
| [ ] | **ระบบอ่านบิลไม่พร้อม:** ใช้ fixture `OCR_NOT_CONFIGURED` | **ระบบอ่านบิลยังไม่ได้เปิดใช้งาน** และแนะนำให้แจ้งผู้ดูแลหรือ **กรอกตัวเลขเอง** | ห้ามถอด API key จาก production เพื่อทดสอบ |
| [ ] | **โหลดหลักฐานไม่สำเร็จ:** ใช้ fixture ที่ไม่มีสิทธิ์หรือไฟล์ทดสอบที่ตั้งใจให้หาไม่พบ | บอกว่าเปิดหลักฐานไม่ได้ ห้ามยืนยัน และมีวิธีลองใหม่/แจ้งผู้ดูแล | ห้ามลบหรือเปลี่ยนสิทธิ์ไฟล์หลักฐานจริง |

เกณฑ์ผ่าน: ผู้ใช้แยกได้ว่า “ไม่มีข้อมูล”, “ยังโหลดอยู่”, “ออฟไลน์”, “สิทธิ์หมดอายุ” และ “ระบบผิดพลาด” ต่างกัน และรู้ว่าต้องทำอะไรต่อโดยไม่ถามผู้พัฒนา

## 6. ตรวจหลัง Merge และ Deploy

| ผ่าน | จุดตรวจ | เกณฑ์ |
|---|---|---|
| [ ] | Repository | Feature branch ผ่าน review และ Merge เข้า `main` แล้ว |
| [ ] | Automated verification | `pnpm verify` ผ่าน 152 tests, TypeScript, Apps Script syntax และ production build |
| [ ] | GitHub Pages | Workflow ของ commit ที่ Merge สำเร็จ และ PWA เปิดได้จาก URL จริง |
| [ ] | Frontend wording | หน้า production ใช้คำตามบทบาทและไม่มีคำเก่า เช่น `Gemini API Key`, `ข้อมูลและการตั้งค่า`, `ข้อตกลงฉบับที่` |
| [ ] | Provider ก่อน Deploy | `testGeminiProviderConnection()` ตอบ `ok=true`, `imageInput=true`, `structuredOutput=true`, `code=GEMINI_CONNECTION_OK` โดยไม่แสดง secret |
| [ ] | Backend health | ตอบ `status=ok`, `release=2026.09.01-ocr-provider-v10`, `schemaVersion=2026-08-production-v3` |
| [ ] | Cache/PWA | ปิดแล้วเปิดแอปใหม่หรือ Hard refresh จากนั้นยืนยันว่าโหลด asset รุ่นใหม่ ไม่ใช่ Service Worker cache เก่า |

การแก้เอกสารหรือ frontend เท่านั้นไม่ต้อง Deploy `Code.gs` ใหม่ หาก `appsscript/Code.gs` ไม่มี Diff ให้ตรวจ Health ว่ายังเป็นรุ่นเดิมและห้ามรัน migration โดยไม่จำเป็น

## 7. งานปฏิบัติการอีก 3 รายการ

รายการเหล่านี้ต้องได้รับการยืนยันจากเจ้าของระบบหรือผู้ดูแลที่มีสิทธิ์ ไม่สามารถสรุปว่าผ่านจาก source code ได้

1. **หมุนเวียนความลับ:** ยืนยันว่ารหัสผ่านหรือ Secret ที่เคยส่งระหว่างการทดสอบถูกเปลี่ยนแล้ว ห้ามบันทึกค่าใหม่ลงเอกสาร
2. **เฝ้าดูเหตุขัดข้อง:** ระหว่างใช้งานแบบควบคุม บันทึกเวลา บทบาท การกระทำ Request ID และ Error ทุกครั้งก่อนสั่งแก้โค้ด
3. **รักษาหลักฐาน:** เก็บ backup ก่อน migration และ E2E audit record ที่ติด Tag ไว้ในพื้นที่ส่วนตัวตามนโยบายของทีม
